# WebDAV 多端安全同步设计

## 背景

当前 WebDAV 同步已经保存 `lastSyncedHash` 和 ETag，并尝试基于本地、远端和上次同步基线进行三方比较。但实际多端使用中出现了错误覆盖：电脑 B 修改并上传后，未修改的电脑 A 点击“立即同步”，A 的旧本地数据反而覆盖了云端新版本，并显示“同步完成”。

同步必须优先保证数据安全：无法证明某一方是唯一更新方时，不得自动覆盖任何一方。

## 目标

- 未修改设备能够自动下载另一设备上传的最新云端版本。
- 只有本地发生变化且云端相对可信基线未变化时，才允许自动上传。
- 本地和云端都变化时进入冲突，禁止自动覆盖。
- 同步基线缺失或不可信时，不猜测版本先后关系。
- 上传优先使用 ETag 条件请求；无 ETag 服务经用户首次确认后使用上传前复查与上传后回读验证。
- 不增加常驻“上传本地”或“下载云端”按钮。
- 同步结果提示明确区分上传、下载、无变化和冲突。

## 非目标

- 不实现字段级或简历级自动合并。
- 不使用设备系统时间判断哪个版本更新。
- 不依赖 WebDAV 服务端提供自定义版本号。
- 不自动解决双方同时修改产生的冲突。

## 核心模型

### 可信同步基线

每台设备独立保存同步元数据：

```ts
interface SyncMetadata {
  concurrencyMode?: 'etag' | 'hash-fallback';
  etag?: string;
  lastSyncedHash?: string;
  lastSyncedAt?: string;
  hasTrustedBaseline: boolean;
  status: SyncStatus;
  lastError?: string;
  conflict?: SyncConflictSummary;
}
```

`lastSyncedHash` 表示该设备最后一次确认“本地业务数据与云端业务数据完全一致”时的内容哈希。`hasTrustedBaseline` 明确区分：

- 已建立可信基线；
- 旧版本遗留、浏览器数据被清理或首次连接，无法确认基线。

为了兼容已有用户，旧同步元数据只有在同时具备有效 `lastSyncedHash` 和 ETag 时，才迁移为可信的 `etag` 基线。显式保存为 `hash-fallback` 的元数据只需非空 `lastSyncedHash`，但该模式只能来自用户明确选择版本，或客户端已经验证本地与远端内容一致的成功同步。

### 哈希范围

哈希覆盖所有 WebDAV 同步的业务数据，包括：

- 全部简历及当前简历；
- 简历原文件；
- AI 配置；
- 通用设置；
- 投递记录。

同步状态、最近同步时间、冲突摘要和导出时间不参与哈希，避免状态自身造成假修改。

界面可维护 `localDirty` 作为即时提示，但同步决策必须通过当前 `localHash` 与 `lastSyncedHash` 比较，不能只相信布尔标记。

## 同步决策

读取本地和远端后计算：

```text
localChanged  = localHash  !== lastSyncedHash
remoteChanged = remoteHash !== lastSyncedHash
```

### 存在可信基线

| 本地变化 | 云端变化 | 动作 |
|---|---|---|
| 否 | 否 | 无变化，刷新 ETag 与同步时间 |
| 是 | 否 | 使用读取时的 ETag 条件上传本地 |
| 否 | 是 | 下载并应用云端数据 |
| 是 | 是 | 进入冲突，不覆盖任何一方 |

### 不存在可信基线

- 远端不存在：创建远端文件，成功后建立基线。
- 远端存在且本地、远端哈希相同：建立基线，不上传也不下载。
- 远端存在且本地、远端哈希不同：进入冲突，不自动覆盖。

### 远端被删除

如果设备曾有可信基线但远端文件不存在，视为远端状态变化，进入冲突；不得自动用本地旧数据重建远端文件。

## 双设备示例

初始 A、B、云端均为 V1，A、B 各自保存可信基线 V1。

1. B 修改为 V2：B 的 `localHash` 与基线 V1 不同。
2. B 同步：云端仍为 V1，因此仅本地变化，安全上传 V2。
3. A 点击立即同步：A 本地仍为 V1，与基线一致；云端为 V2，与基线不同。
4. A 判定为“仅云端变化”，下载 V2，且不发送 PUT。
5. A 应用 V2 后将本地哈希、`lastSyncedHash` 和 ETag 更新为 V2 对应值。

## 并发保护

ETag 模式下，所有覆盖现有远端文件的上传必须携带读取阶段获得的 ETag；hash-fallback 模式则执行上传前 hash 复查和上传后回读验证：

```http
If-Match: <remote-etag>
```

如果读取后另一台设备更新了远端，服务器返回 412 或等价冲突。客户端不得无条件重试 PUT，而应重新读取远端摘要并进入冲突状态。

首次创建远端文件使用“仅当文件不存在”的条件语义；如果创建期间另一台设备已经建立文件，也必须转为冲突或重新进行安全判定。

## 用户界面

正常状态只保留“立即同步”。不常驻显示强制上传或强制下载按钮。

冲突状态继续显示：

- 本地摘要；
- 远端摘要；
- 使用本地；
- 使用远端；
- 暂不处理。

无可信基线时使用明确文案：

> 无法确认本地与云端的先后关系，系统未覆盖任何数据。请核对摘要后选择保留哪一份。

成功提示按实际动作区分：

- 已上传本地更新；
- 已下载云端更新；
- 本地与云端已一致。

## 错误处理

- 下载内容解析或校验失败：保留本地数据，状态设为错误。
- 应用远端数据失败：不更新同步基线。
- 条件上传失败：不更新同步基线，进入冲突或错误状态。
- WebDAV 网络失败：保留上次可信基线，以便下次重试。
- 只有操作完整成功后，才更新 `lastSyncedHash`、ETag 和 `lastSyncedAt`。

## 测试策略

### 双设备核心回归

模拟 A、B 两套独立同步元数据与同一个远端：

1. A、B 与远端从 V1 建立基线。
2. B 修改为 V2 并上传。
3. A 保持 V1 并同步。
4. 断言 A 下载 V2。
5. 断言 A 没有发送 PUT。
6. 断言 A 的可信基线更新为 V2。

### 其他覆盖

- 仅本地变化时条件上传。
- 双方变化时冲突且不发送 PUT。
- 无可信基线但内容不同进入冲突。
- 无可信基线但内容相同建立基线。
- 已有可信基线而远端被删除时进入冲突。
- ETag 在读取后变化时禁止覆盖。
- 保存 WebDAV 设置和测试连接不会创建或重置同步基线。
- 下载失败或应用失败时不更新基线。
- UI 根据同步动作展示准确提示。

## 验收标准

- 电脑 B 修改并上传后，未修改的电脑 A 点击“立即同步”会自动下载 B 的版本。
- 任何无法确认单边更新的场景都不会自动覆盖云端或本地。
- ETag 模式下自动上传受条件请求保护；hash-fallback 模式执行上传前复查与上传后验证，并明确不提供原子并发保证。
- 用户无需新增常驻方向按钮即可完成正常多端同步。


## 规格变更：无 ETag 的 hash-fallback 模式（2026-09-08）

### 模式与可信条件

同步元数据持久化 `concurrencyMode`：

- `etag`：可信基线必须同时包含非空 `lastSyncedHash` 与非空 ETag。
- `hash-fallback`：可信基线必须包含非空 `lastSyncedHash`，且只能由用户明确选择某一版本，或本地与远端内容已经成功校验一致后建立。

首次发现远端存在、没有 ETag 且本地与远端内容不同，不自动应用或上传。状态进入冲突，保存两侧摘要及 `missing-etag-confirmation` 原因，UI 说明服务未提供 ETag，只需首次确认，并提供“使用本地”“使用远端”“暂不处理”。

用户选择远端后，客户端应用并校验远端内容，将远端 hash 保存为可信 `hash-fallback` 基线。用户选择本地后，客户端再次 GET 并确认远端 hash 未变化，再上传本地，随后 GET 回读并校验上传结果，成功后保存本地 hash 为可信 `hash-fallback` 基线。

### 后续三方同步

建立 `hash-fallback` 基线后，继续按 `localHash`、`remoteHash` 与 `lastSyncedHash` 三方判定：

- 仅远端变化：自动下载并验证，不发送 PUT。
- 仅本地变化：上传前重新 GET，确认远端 hash 仍等于本次基线；上传后重新 GET，确认远端 hash 等于本地 hash。
- 双方变化：进入冲突，不自动覆盖。
- 双方未变：刷新成功时间并保持可信基线。

该模式不能提供 ETag 条件写入的原子并发保证，用户已明确接受此限制。任一后续 GET 或 PUT 流程取得有效 ETag 时，成功同步后自动升级并持久化为 `etag` 模式；之后恢复 `If-Match` 条件写入保护。
